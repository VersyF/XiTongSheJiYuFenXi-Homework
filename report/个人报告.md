## 1. `push`

`push` 定义的是**自动触发条件**：只有当 `main` 分支被推送，并且改动涉及 `docs/**`、`mkdocs.yml`、`requirements.txt` 或 `.github/workflows/deploy.yml` 这几个路径时，工作流才会自动跑。

它的好处是**只对会影响网站的内容做部署**。比如你只改 `report/README.md` 或根目录 `README.md`，因为不在这些路径里，就不会触发部署，避免无意义的构建和发布。

## 2. `workflow_dispatch`

`workflow_dispatch` 允许你在 GitHub 的 `Actions` 页面**手动点按钮运行**这个工作流，不依赖 push。

它主要用于：

- 第一次部署失败后，改完配置手动重试

- 排查问题时手动跑一次看日志

- 不想再提交一次代码也能重新部署

## 3. `build`

`build` 是一个任务（job），负责**生成可部署的网站文件**。它的步骤依次是：

- `Checkout source`：把仓库源码拉取到 Actions 运行环境

- `Set up Python`：配置 Python 3.12

- `Configure Pages`：读取 Pages 相关配置，为后续部署做准备

- `Install dependencies`：按 `requirements.txt` 安装 MkDocs 和 Material 主题

- `Build documentation`：执行 `mkdocs build --strict`，把 `docs/` 构建成 `site/`

- `Upload site artifact`：把 `site/` 目录打包成 artifact，供 deploy 任务使用

## 4. `needs: build`

`needs: build` 表示 `deploy` 任务**依赖 `build` 任务**：只有 `build` 成功完成，`deploy` 才会开始。

## 5. `pages: write`、`id-token: write`

这两个是 `deploy` 任务里的**权限声明**：

- `pages: write`：允许工作流**写入 GitHub Pages**，也就是真正发布网站

- `id-token: write`：允许获取 OIDC 身份令牌，GitHub 官方 Pages 部署需要用它做身份验证

## 6. `github-pages`

`environment: name: github-pages` 指定部署使用的**环境**叫 `github-pages`。

这个环境的作用是：

- 在仓库的 `Environments` 里**记录和管理部署**

- 保存部署历史

- 通过 `url: ${{ steps.deployment.outputs.page_url }}` 把**网站访问地址**显示在 Actions 运行记录里
